日付: 2026-10-13。

失敗8件はRQMCによる追加調査で通ったが、この追加調査を独立した受入合格へ読み替えない。
実行記録は [集約JSON](vega-kt-holdout-v0.1.json) に保存する。

## 失敗の内容と追加調査

- 4区間、seed 104729: Asian Call、過去fixing付きAsian Call。
- 6区間、seed 130363: European Call/Put、Lookback Call、3種類のLookback Put。

8件ともGamma回復の検査は通り、条件付きADとの節点別照合で停止した。
4区間ではvariance row 2 / node 12、6区間のEuropeanではrow 4 / node 9に差が出た。
節点は0始まり。判定の観測値・標準誤差・上限は集約JSONに残した。

不合格8件の市場Vega推定値を、診断目的で独立価格差分とも比較した。
許容上限に対する差の最大比率は約0.532で、この照合だけでは失敗しなかった。
これは内部検証を省略する理由にはならない。不合格商品のリスクは利用不可のままとする。

| 追加調査 | 4区間の失敗2件 | 6区間の失敗6件 |
|---|---|---|
| pseudo-MC標本数4倍 | 2件とも計算量上限で拒否 | 4件は上限で拒否、2件は照合不合格 |
| pseudo-MC標本数2倍 | 2件合格 | 6件不合格 |
| RQMC 256点 × 16 scramble、antithetic、bridgeなし | 2件合格 | 6件合格 |

追加調査は計24件。積分分割数、6標準誤差による比較、絶対誤差上限、計算量上限は緩めていない。
RQMCの独立標本はscramble平均であり、点の数を独立標本数として扱わない。
RQMCの条件付きAD参照には既存の追加標本計算があるため、単純に同じ計算量と見なさない。

これは失敗例を見てから行った方式選択の調査であり、採用する方式の独立受入ではない。
通常providerは現在もpseudo-MCの4/6区間を扱う。RQMCを通常providerへ接続する前に、
別の未使用seedで全商品・合同共分散・損益・保存と再開を確認する必要がある。

## 年間計測

[受入精度用の計測方針](../../fixtures/backtesting/accepted-performance-policy-v0.1.json)と
[計測スクリプト](../../scripts/benchmark_accepted_replay.py)を追加した。
対象10商品・ヘッジ候補20商品、252平日、計7,560リクエストの合成入力を使う。
市場祝日は除外しない。2026-01-05から2026-12-22、満期は2027-02-09。

6区間・33 LV節点・3満期×5 IV節点、2,048独立pseudo-MC標本、
明示的all_rows拡張、商品間共分散検査を使用する。
これは従来の診断用5×9グリッドの性能測定と異なる負荷であり、速度を直接比較しない。
rolling満期座標を使うため、固定絶対満期が対応しない日のIV損益は理由付きで未説明になる。

初回の2日分の事前実行では、初日の30商品の個別リスク検証は合格した。
しかし数量最適化が10,000反復で収束せず、projected gradientは約2.24e-5、上限は1e-8だった。
日次処理は巻き戻され、確定済み日次台帳・注文は0件。
商品間の合同リスク計算へ到達していないため、初回の397.6秒を年間所要時間へ外挿しない。

同一の保存入力に対し、最適化目的・ridge・許容誤差を維持して反復上限だけ100,000へ増やす
[再検証スクリプト](../../scripts/probe_annual_solver_budget.py)で再実行した。
最適化と30商品の合同リスク計算は通過したが、数量を反映したbucket標準誤差が
**36.0471 > 上限10.0** となり、`joint_risk_quality` で初日の処理を取り消した。
確定した台帳・注文は引き続き0件。許容誤差を広げて継続する変更は行っていない。

| 反復上限100,000の再実行 | 実測 |
|---|---:|
| 個別リスク30件 | 392.0秒 |
| 30商品の合同リスク1回 | 256.9秒 |
| 失敗までの日次実行全体 | 653.7秒 |
| プロセス最大RSS | 825.1 MiB |
| 入力・失敗状態を含む保存出力 | 113,372,892 bytes |

結果は集約JSONの `annual_solver_budget_probe` に記録した。
年間252日通期の実測と、承認された時間予算に対する性能受入は未完了。
計測中は他の数値検証も実行しており、所要時間には処理の競合を含む。
個別リスクと合同リスクでGamma計算を再実行しているため、受入精度を維持した結果の共有が
今後の性能改善候補になる。ただし、まず今回の合同精度不足を解消する必要がある。

## 再実行と証跡

既存の参照証跡が必要。各実行は新しい出力先を指定する。
検証器は不合格を保存して非ゼロ終了し、過去の結果へ上書きしない。

```sh
.venv/bin/python scripts/check_portfolio_holdout.py \
  --case regression_4 --output /tmp/new-holdout-regression-4.json
.venv/bin/python scripts/benchmark_accepted_replay.py \
  --pilot --output /tmp/new-accepted-annual-pilot
```

追加した手順の試験6件は合格。参照の改変拒否、既使用seedの拒否、商品とnative入力の一致、
検証失敗の記録、計算量上限による拒否後の調査継続、JSON保存を検査した。
元の本体試験298件を今回すべて再実行したという意味ではない。

全ケースの証跡を [集約器](../../scripts/summarize_portfolio_holdout.py)で照合する。
単に合格件数を足さず、全120パネルの存在、重複、source・policy・参照hash、
失敗件数、年間計測の停止状態を検査する。不完全な実行を合格へ集約しない。
